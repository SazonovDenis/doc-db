# doc-db: usage

## How it works

doc-db is an external tool: the scripts live here, your database description lives in your project.

The project is your current directory (or the one given with `--root`); put your database description in `doc/db`
(or the directory given with `--doc`). Your `doc/db` holds three files:

| File             | Contents                                                                          | Edited by                    |
|------------------|-----------------------------------------------------------------------------------|------------------------------|
| `db-desc.yaml`   | Descriptions of tables and columns, diagrams, references to Java constant classes | a person                     |
| `db-struct.yaml` | Physical structure: tables, columns, types, nullability, PK, FK, allowed values   | generated by `import-struct` |
| `db-consts.yaml` | Java class constants from `constants_from` (needed only if there are any)         | generated by `import-consts` |

Your database description `db-desc.yaml` is laid over `db-struct.yaml`, constants are taken from `db-consts.yaml`,
and the `gen-html` script generates `_site/db.html` in the current directory from them (or the file given with `-o`).

## How to connect it

Your project connects the tool with its own script, for example:

```bash
TOOL="${DOC_DB:-/home/user/projects/doc-db}"
cd "$ROOT"
"$TOOL/import-struct" --liquibase app-database/src/main/resources/db/changelog/db.changelog-master.xml -o doc/db/db-struct.yaml
"$TOOL/gen-html" -o _out/doc/db-doc.html
```

### Must be installed to run

- Python 3 + `pip install pyyaml jinja2`
- `psql` - only if you read the structure of a real database with `import-struct --db`
- Java - for diagrams; PlantUML ships with the tool: `lib/plantuml.jar`. Without it the HTML is generated without
  diagrams.

### Documentation generation steps

From the project root:

```bash
# 1. Import the database structure - from one of the sources
import-struct --flyway backend/src/main/resources/db/migration
import-struct --liquibase path/to/db.changelog-master.xml
import-struct --db postgresql://user@localhost/dbname        # password - in PGPASSWORD or ~/.pgpass

# 2. Import Java class constants - if db-desc.yaml has constants_from with classes
import-consts

# 3. Generate the HTML database documentation
gen-html
```

### import-struct

Reads the actual DB structure and stores it.

- **Flyway** - `V<version>__*.sql` files in ascending version order; several directories are allowed. Parsed:
  `CREATE TABLE`, `ALTER TABLE` (ADD/DROP/ALTER/RENAME COLUMN, ADD/DROP CONSTRAINT, RENAME TO), `DROP TABLE`.
  `INSERT`, `UPDATE`, indexes and the rest do not change the structure and are skipped.
- **Liquibase** - XML changelog: `include` and `includeAll` in order; createTable, addColumn, dropColumn,
  renameColumn, renameTable, dropTable, modifyDataType, add/dropNotNullConstraint, add/dropPrimaryKey,
  add/dropForeignKeyConstraint; FK both as a separate operation and in a column's `<constraints>`. Names are matched
  case-insensitively (as Liquibase and PostgreSQL do); the documentation uses the spelling from `createTable`.
- **Live database** - the PostgreSQL catalog via `psql`. The most accurate source.

Whatever cannot be parsed (unknown table, column, operation) is written to stderr as `WARN ...` instead of being
silently skipped.

The service tables `flyway_schema_history`, `databasechangelog`, `databasechangeloglock` are not included.
Types are normalized to one spelling: `varchar(50)`, `integer`, `bigint`, `numeric(6,2)`, `timestamptz`, `text[]`.
`values` - allowed values from `CHECK (col IN (...))`. Composite FKs are not shown.

```yaml
tables:
  wagons:
    primary_key: [ id ]
    columns:
      id: { type: uuid, required: true }
      depot_id: { type: uuid, references: depots }
      status: { type: varchar(20), required: true, values: [ IN_SERVICE, IN_REPAIR, RESERVE, OUT_OF_SERVICE ] }
```

### import-consts

Collects the constants of the classes listed in `constants_from` in `db-desc.yaml` (for tables and columns). A class
is looked up by FQN in the source directories; `public static final` constants with a comment before them
(`/** ... */` or `//`) are taken from it. Class not found - error, exit code 1.

```yaml
classes:
  kz.example.Status:
    file: app/src/main/java/kz/example/Status.java
    constants:
      - { name: NEW, value: '1', description: 'New' }
```

### Database description format in db-desc.yaml

```yaml
title: "Title"
subtitle: "Subtitle"
diagrams:
  group_name:
    title: "Diagram title"
    description: "Explanation"
    tables: [ Table1, Table2 ]
tables:
  TableName:
    title: "Short name"
    description: |
      Multi-line description.
    constants_from: kz.example.Constants   # Java class with constants (optional)
    columns:
      column_name:
        title: "Short name"                # on the diagram next to the field name; if absent - description
        description: "Field description"
        constants_from: kz.example.Status  # optional
      status:
        title: "Status"
        constants_from: doc/dict/statuses.tsv  # or a .tsv dictionary
      other_column: "Short form: a string instead of description"
```

`constants_from` - a Java class (FQN) or a `.tsv` file (path from the project root). From a `.tsv`, rows without the
header are taken, the first three columns being value, name, explanation; `import-consts` skips such files, `gen-html`
reads them itself.

Column order in the HTML - the primary key, then as listed in `db-desc.yaml`, the rest - references (FK) alphabetically, then
the others alphabetically.

### Checks during generation

Before generating, `gen-html` checks that `db-desc.yaml` contains nothing extra:

- **[extra table]** - the table is not in the structure (removed or a typo), including in a diagram's list;
- **[extra column]** - the column is not in the structure;
- **[unknown key]** - a key not from the list above (for example, `descripton`);
- **[no file]** - the `.tsv` file from `constants_from` does not exist;
- **[no constants]** - the class from `constants_from` is not in `db-consts.yaml`: the file is outdated, rerun
  `import-consts`.

On errors the HTML is not generated, exit code 1. Undocumented tables and columns are not an error: `gen-html` only
prints their count. With `--strict` they are errors too, with a list:

- **[missing table]** - the table is not in `db-desc.yaml`;
- **[missing column]** - the column is not in its table's description.

### Command options (you most likely don't need them)

`--root DIR` (`import-consts`, `gen-html`) - the project root, if not run from it; `.tsv` files from `constants_from`
and Java sources are looked up from it. `--doc DIR` - the directory of the yaml files, if not `doc/db`.

`gen-html -t FILE -o FILE -D NAME=VALUE` - another template, output file and template variables (`-D` may be
repeated). Your own template may extend `template.html.j2` (`{% extends "template.html.j2" %}`) and override the
blocks `style`, `page` (the whole page), `toc` (contents), `content` (diagrams and tables) - for example, to embed
the page into a shared documentation site.

Labels language - `--lang XX` (shortcuts `-en`, `-ru`); English is the default. The template is one, labels come
from `lang/XX.yaml` into the `t` variable (`{{ t.tables }}`); keys missing in a language are taken from `en.yaml`.
A new language is one more `lang/XX.yaml` file. `--labels FILE` - the project's own labels over the language ones.
Your own template gets `t` too.

The diagram cache is `.plantuml-cache` in the project root (add it to `.gitignore`). For each diagram `gen-html` first builds its
PlantUML text (tables, fields, relationships); the SVG name in the cache is the sha1 of that text. If the structure or
descriptions that went into a diagram change, the text changes and so does the name: there is no such SVG, PlantUML
runs. The other diagrams come from the cache: a rebuild takes seconds instead of ~40 s. SVGs the build did not need
are deleted. After a PlantUML upgrade the cache can be deleted entirely.

`import-struct -o FILE` - write to another file; `--schema` - schema for `--db` (default `public`).
`import-consts --src DIR ...` - Java source directories (default `*/src/main/java` of the project modules); `-o FILE`.
